# 业务排程预览与重新规划

```text
task-planning/
├── README.md         # 前端与业务后端的规划范围、确认及替换约定
└── api-examples.json # 默认、新作业、单项和多项重新规划请求与提案合成样例
```

`POST /api/planning/proposals` 须登录，请求为对象；省略 `taskIds` 和 `replan` 时按账号默认范围规划。内部规划 Harness 仍使用 [共享协议的 2.0 格式](../../docs/backend-harness-alignment.md)，此目录描述浏览器调用的业务 API。

| 请求字段 | 格式及含义 |
| --- | --- |
| taskIds | 可选，非空、无重复的任务 ID 字符串数组；限定当前账号有 DDL 的任务 |
| replan | 可选布尔值，默认 false；true 时纳入已有安排的任务 |

默认范围排除已完成、已取消、已安排和标记“无需规划”的任务；`replan: true` 纳入已有安排但仍排除已完成、已取消任务。显式指定 taskIds 并重新规划时视为用户选择，可纳入“无需规划”的任务；未知或已完成任务编号返回 400。

200 提案回应包含 `requestId`、`estimates`（任务 ID 到预计分钟的映射）、`blocks`（taskId/title/startAt/endAt）、`warnings`、`priorityOrder` 及 `replannedTaskIds`。`replannedTaskIds` 列出确认后将替换未来时段的任务；未生成新时段的任务不列入。样例中的日期均为合成固定值，回放测试应换为未来时间。

生成预览不改动任务或日历。重新规划时，所选任务尚未开始的时段暂不作为占用时间；已开始的时段和其他任务的安排始终作为占用时间。若某任务没有生成新时段，其旧安排须保留并参与最终冲突校验。

`POST /api/planning/apply` 请求为 `{requestId: 提案编号}`；服务端按账号及任务集合版本确认，原子移除待替换时段并写入新时段，回应为 `{value: 完整任务数组, version: 新任务集合版本}`。DDL、任务状态和其他任务安排不因替换时段改变。

同一方案再次确认、任务版本变化、待替换时段在等待期间已经开始、新时段已过期均返回 409，不写入日历。模型失败、空方案及取消预览均保留原安排。待替换时段编号只存于后端方案，不信任前端传来的删除清单。

前后端测试读取本目录的请求样例，后端回归测试验证确认前不修改日历、仅替换选中任务的未来安排、版本冲突和占用冲突时保留原值。
