# 待核对任务的用户操作

复用 `POST /api/recognition/candidates/{id}/resolve`。候选仍按原来源契约保存，清单中的待核对行是当前账号候选的展示投影，不因查看而自动入库。

用户在普通任务编辑器保存实际修改时，发送既有 `action: "create"`、`reviewed: true`、候选 `version`、工作区 `tasks_version`、`target_id: null` 和用户编辑后的 `draft`。仅查看、取消或未改变字段不发送确认请求。新增或处理方式不明确的候选可由用户接受为普通任务；更新、延期和取消继续明确选择目标与变更动作。

用户直接勾选待核对任务完成时，在上述请求上增加可选布尔字段 `complete: true`。服务端在同一事务中创建任务、将其设为 `status: "completed"`、以北京时间当天填写 `completedAt`、保留来源及 `recognitionHistory`，并将候选设为 `applied`。通知的 `completed` 沿用已阅读语义。省略该字段保持现有新增未完成任务的行为。

`complete` 仅允许手动确认的新增操作使用；值必须为布尔，`reviewed` 必须为 `true`，不得与 `auto_apply: true`、忽略或其他变更动作组合。版本冲突或保存异常时整体回滚，不得创建任务后把候选留在待核对状态，或移除候选却未保存完成状态。完全相同请求沿用原有幂等确认，不重复创建任务、历史或增加工作区版本。

响应维持 `{ "batches": [...] }`。前端随后刷新工作区，以任务的 `recognitionHistory.storageId` 定位确认后的普通任务；已完成任务进入已完成列表。重新打开已完成任务只改普通任务状态，不恢复待核对标记。工作区刷新失败时说明操作已保存并要求重新读取，不重新派发新增操作。

忽略及撤销继续使用现有 `ignore` / `reopen` 和候选版本，不视为确认任务。所有请求沿用登录会话、账号隔离及服务端版本校验。
