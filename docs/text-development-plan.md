更新日期：2026-09-22。本文规定接下来如何实现与交付，不表示功能已经实现。当前产物为需求、任务拆分与计划；尚未运行真实模型。

范围及输出语义以[需求基线](text-extraction-requirements.md)为准，Issue 对照与完整验收条件见[冲刺任务](sprint-1-text-processing.md)。看板为 [NiuMa Manager](https://github.com/users/Craneplayz/projects/2)，迭代字段由负责人维护。

## 二、阶段 A：冻结第一版约定

主要任务：[TXT-01 / #3](https://github.com/Craneplayz/niuma-manager/issues/3)。样本规则同时支持 [TXT-06 / #8](https://github.com/Craneplayz/niuma-manager/issues/8)。

开发步骤：

1. 同步上游最新贡献规则，检查现有目录、技术栈及工作区变更。已有本地文档需要保留并与上游新增文档合并。
2. 为输入、候选任务、处理结果建立带版本的草案。确定必填项、空值、原始时间、日期精度、日期性质、证据与错误类型。
3. 明确无任务、部分成功、失败的差别；文本呈现可变，内部语义保持稳定。
4. 建立合成样本及人工标注说明：一条消息可以有多项待办，无日期仍保留，取消是变更信息，纯聊天可无任务。
5. 把未确认规则集中记录，向上下游提供同一组示例；未确认的字段不得称为已达成团队接口协议。

检查：逐项核对需求覆盖；输入与输出示例互相对应；日期推断说明完整；文档链接可访问；示例无私人内容与凭据。

计划提交：`docs(text): define extraction contract and sprint plan`，正文关联 `Refs Craneplayz/niuma-manager#3`。标注集另在 #8 的分支提交，避免将不同任务混入同一个提交。

退出条件：接口草案、边界与示例可供队友评审；剩余争议均有具体问题及默认处理，不影响后续接口实现。

## 三、阶段 B：搭建可离线验证的处理骨架

主要任务：[TXT-02 / #4](https://github.com/Craneplayz/niuma-manager/issues/4)。依赖 #3 的字段草案。

开发步骤：

1. 依据仓库现有技术栈选择实现语言；仓库没有既定实现时记录选择理由，避免为运行环境未定而提前加入服务端框架。
2. 分离输入对象、Agent 调用接口、业务处理、结果校验和文本呈现。先提供本地文件或标准输入入口，具体方式随技术栈选择。
3. 提供确定性离线替身，模拟正常结果、多任务、格式错误、超时和连接失败；入口明确显示当前调用模式。
4. 将模型标识、地址、超时、重试上限等集中配置。真实适配器参数不足时明确报“未配置”，不能悄悄返回模拟成功。
5. 定义有限重试及批量失败处理：单条失败可追踪，不吞掉整批其他结果；默认日志只保留处理标识、版本、耗时和错误类别。

检查：调用层替换后业务规则无需改动；离线测试不访问网络；空白输入、缺少字段和模型失败分别可识别；多个用户的上下文不得混用。

计划提交：

- `feat(text): add configurable agent boundary and offline runner`，包括接口与对应行为测试。
- `test(text): cover timeout and partial batch failures`，仅在形成独立新增覆盖时单独提交；少量相关测试随实现一起提交。

退出条件：队友无需模型密钥即可跑通合成输入与离线结果；清楚看到哪些能力仍等待实际适配器。

## 四、阶段 C：实现核心识别与 skills

主要任务：[TXT-04 / #6](https://github.com/Craneplayz/niuma-manager/issues/6)、[TXT-03 / #5](https://github.com/Craneplayz/niuma-manager/issues/5)。先确定共享规则，再实现调用编排；规则不在提示词、代码与 skill 中各写一套相互冲突的版本。

开发步骤：

1. 编写文本任务识别 skill：适用范围、输入约定、任务识别步骤、时间与来源规则、结果要求、失败处理、正反例。
2. 如采用网络已有 skill，先检查来源、许可证、依赖与工具权限，再裁剪到本任务；不为凑数量引入多个重复 skill。
3. 处理零到多任务，保留报名、加群等待办；需要合并或拆分前置步骤时保留依据，规则可调整。
4. 根据每条消息的发布时间理解相对日期；只有日期时保留日期精度。活动时间作为参考完成时间时标为推断，缺少参照或信息冲突时要求核实。
5. 从输入与上下文保留来源证据；无法确定课程全称或原文链接时留空或标注推断，不补造来源。
6. 识别延期、取消及对象指代。输出候选变更信息，不执行数据库或前端更新；无法匹配旧任务时标记待核实。
7. 将用户消息视为分析材料，其中的“忽略规则”“调用工具”等文字不能改变 Agent 的任务或权限。

检查：加群样本不得把上课时间标成明确入群截止时间；无日期待办不漏掉；跨日和跨年换算有固定基准；上下文引用有证据；无完整来源仍能输出；恶意指令不能触发无关操作。

计划提交：

- #6：`feat(skills): add text task extraction rules and examples`。
- #5：`feat(text): extract task candidates with source evidence`。
- #5：`feat(text): preserve deadline uncertainty and change intent`，包括相关日期与上下文回归测试。

退出条件：规则、程序行为和评测预期一致；skill 文件准备就绪与实际加载成功分别记录，真实加载验证交由 #9。

## 五、阶段 D：校验、文本输出与模型连接

输出任务：[TXT-05 / #7](https://github.com/Craneplayz/niuma-manager/issues/7)。早期按约定开发，#5 完成后用真实识别结果联调。

1. 校验结果字段、日期格式、日期精度与状态一致性。关键字段损坏时给出明确错误，不能伪装成“没有任务”。
2. 文本稳定展示任务、课程/项目、明确截止或参考时间、来源、核实原因。未知日期直接标注未知，不补默认截止时间。
3. 多条任务保持清楚边界；保留处理标识，便于上下游排查。内部对象可在后续增加 JSON 呈现而不重写识别流程。
4. 对模型错误采用受限重试或明确失败；局部无效结果保留错误记录，并说明是否产生可用任务。

检查：正常、无任务、多任务、未知日期、推断日期、日期冲突、部分成功与失败各有输出样例；后续调用方能区分状态。

计划提交：`feat(text): validate results and render reviewable text`，包括输出语义与错误路径测试。

连接研究：[TXT-07 / #9](https://github.com/Craneplayz/niuma-manager/issues/9)，有效研究时间上限 4 小时，等待外部信息另记。

1. 收集可信环境、真实模型标识、接口协议、认证方式及 Codex 配置方式；选定模型保持不变。
2. 查证并实测接口兼容性、调用权限、skill 加载和输出解析。先用合成样本验证，私人文本只在符合已确认数据约束的环境中处理。
3. 记录版本、脱敏配置、输入样例、实际输出、耗时、失败原因及成本信息（若可获得）；每条结论标出证据。
4. 给出可行、不可行或信息不足的结论以及后续动作。若实际适配工作超出研究时间或原验收范围，在同一仓库补充关联任务，不悄悄扩大研究 Issue。

计划提交：`docs(research): record Codex provider compatibility findings`；确有可复用且经过验证的适配代码时另提交 `feat(text): add verified Codex agent adapter`，并关联实际负责该实现的 Issue。

退出条件：研究结果可以独立评审。完整产品验收另外要求真实调用、skill 加载和真实质量评测完成；“研究有结论”不能替代这些条件。

## 六、阶段 E：评测、修复与交付

主要任务：[TXT-06 / #8](https://github.com/Craneplayz/niuma-manager/issues/8)、[TXT-08 / #10](https://github.com/Craneplayz/niuma-manager/issues/10)。

评测工作：

1. 先建议准备 30–50 条合成或已脱敏样本，覆盖三个来源与所有核心场景；此数量是起步建议，不是已确认的验收门槛。
2. 为每条样本人工标注预期待办、日期及其性质、来源证据与可接受的差异。预先规定任务匹配方法，避免只凭文字相同与否评分。
3. 开发样本与独立验收样本分开。用户补充的私人原始数据留在批准的环境，仓库只保存可公开使用的合成样本或合规脱敏数据。
4. 程序测试与真实模型评测分开运行、分开报告；报告样本数、任务召回率、精确率、日期错误数、不确定性漏标数、失败率及可获得的耗时/费用。
5. 召回率以人工标注任务为分母，精确率以模型输出候选任务为分母。无任务样本单独检查误报，不通过“全部当任务”提高表面召回率。
6. 每个已定位的关键漏报先增加可复现样本，再修复、跑相关测试与固定回归。模型、提示词或 skill 改动后重新运行固定质量集。

建议验收原则：固定核心场景没有已知关键漏报；确定性程序与契约检查通过；模型质量报告诚实列出剩余问题。具体数值阈值在看到人工样本后与负责人确定，不提前虚构准确率承诺。

计划提交：

- `test(text): add annotated fixtures and recall evaluation`。
- `fix(text): retain actionable tasks without explicit deadlines` 等针对实际发现问题的提交；名称应描述真实修复。
- `docs(text): add usage guide and sprint acceptance report`。

交付说明至少包含：安装与运行、配置、离线/真实模式差异、输入输出例子、隐私约束、测试复现、已知限制、未完成依赖、失败排查以及下游对接入口。

退出条件：其他成员可按说明独立复现；对应 PR 完成非作者评审并合并；Issue 验收项与看板状态一致。未完成项保留关联任务和下一步，不用一句“基本完成”掩盖缺口。

## 七、每个 Issue 的开发、检查、commit 与 PR 流程

1. **选定任务**：检查 Issue 的验收、依赖与当前状态，只把实际开始的主任务设为 In progress；记录计划和阻塞。
2. **检查工作区与基线**：查看当前分支、未提交改动、远程指向；保留已有工作。同步队长仓库默认分支并读取最新团队规则，不覆盖本地 README 或团队新增文档。
3. **建立分支**：每个 Issue 独立分支，Codex 默认 `codex/<issue>-<purpose>`。从已核实的最新基线开始；依赖尚未合并时优先等待评审或在 PR 中明确依赖，不混入无关提交。
4. **先确定行为再实现**：功能工作以输入、预期输出、失败方式为依据，增加必要的行为测试。文档修改只检查内容与链接，不为凑测试创建无意义用例。
5. **执行检查**：运行改动相关测试、仓库规定的格式/静态检查；影响公共接口、模型规则或 skill 时运行固定回归。失败须修复或明确阻塞，不能记成通过。
6. **审查差异**：检查修改范围、错误处理、隐私数据和示例；检查是否意外改动配置、生成文件或他人工作。用 `git diff --check` 检查空白错误。
7. **暂存并 commit**：逐项暂存相关文件，检查暂存差异与 `git diff --cached --check`。一条提交表达一个完整目的，相关测试随实现提交；使用 `feat/fix/test/docs/refactor` 等类型并在正文关联上游 Issue。
8. **提交后核对**：检查最后提交的文件列表、提交说明和剩余工作区改动。测试结论应对应本次提交，不能沿用修改前的结果。
9. **推送并创建 PR**：推送到个人 fork 分支，向队长仓库核实后的默认分支发起 PR。使用团队模板，写明结果、关联 Issue、验证方式、风险和未完成项。部分完成使用 `Refs`，完整覆盖才使用 `Closes`。
10. **评审修订**：至少一名非作者评审。按反馈在同一分支追加清楚的修订提交，再执行受影响检查；不擅自强推改写共享历史，也不自作主张合并。
11. **验收与关闭**：由有权限的维护者按团队约定合并，核对验收与 Issue 关闭结果，再将 Project 更新为 Done。部分交付、等待环境或仅提交 PR 都不能标成 Done。

本计划不要求固定 commit 数量。较小、完整、可解释的提交优先；不把每次生成文件都做成提交，也不把一周全部修改塞进一次提交。
